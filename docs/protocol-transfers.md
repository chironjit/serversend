# Transfer, catalog and queue contract

This is the v1 specification for the later storage/client implementations. Shared wire types, structural validation and the standard transfer/catalog runtime are implemented. Private storage, version/trash controls and event streaming remain later features. General encoding, errors, ownership and pagination follow [protocol foundation](protocol-foundation.md); credentials and trust follow [identity](protocol-identity.md).

## Route and authorization table

All paths below are relative to `/api/v1`. Every route requires an active account/device session, current revocation checks and account ownership, except the public capabilities/identity-proof routes. IDs in paths must pass the canonical identifier validator before storage access. No filename is ever an object path. Idempotency keys are scoped by authenticated account and operation; they never confer authorization.

| Method and route | Input | Success/result | Replay policy |
| --- | --- | --- | --- |
| `POST /uploads` | `CreateUploadRequest`, `Idempotency-Key` | 201 `Upload`; exact replay 200 same upload | Same key plus same validated intent returns the same identity/reservation |
| `GET /uploads/{upload_id}` | None | 200 `Upload` | Read-only; reconcile uncertain creation/finalization/cancellation |
| `GET /uploads/{upload_id}/missing` | `limit`, `cursor` | 200 `MissingChunks` | Stable snapshot of missing index ranges |
| `PUT /uploads/{upload_id}/chunks/{index}` | Exact binary body, `Content-Length`, `ServerSend-Chunk-SHA256` | 201 `ChunkAcknowledgement`; identical retry 200 | Immutable by upload/index; exact length/hash match required |
| `POST /uploads/batch` | `ServerSend-Batch-Header-Bytes: N`; N bytes of `BatchUploadRequest` JSON, then each file's bytes in order | 200 `BatchUploadResponse`, one result or error per file in order | Per-file `idempotency_key`; a replayed key returns its recorded result |
| `DELETE /uploads/{upload_id}` | No body | 200 `Upload` in `cancelled` state | Repeated cancellation returns recorded state; cannot cancel terminal/finalizing work |
| `POST /uploads/{upload_id}/finalize` | Exact `Manifest` body, `Idempotency-Key` | 200 `FinalizeResult`, including a preserved `conflicted` outcome | Same key/body returns the recorded immutable result |
| `GET /files/{file_id}/versions` | `limit`, `cursor` | 200 `VersionPage` | Stable snapshot ordered by opaque version ID |
| `GET /files/{file_id}/versions/{version_id}/manifest` | None | 200 `Manifest` | Exact stored representation; validate digest from `VersionInfo` |
| `GET /files/{file_id}/versions/{version_id}/chunks/{index}` | None | 200 binary body | Full immutable chunk, verified against the manifest |
| `GET /catalog` | Optional `parent_id`, `trashed=false`, `limit`, `cursor` | 200 `CatalogPage` | Stable snapshot ordered by opaque entry ID |
| `GET /catalog/changes` | `after` revision string, `limit`, `cursor` | 200 `CatalogChanges` | Stable revision interval; restart full refresh if history expired |
| `POST /catalog/directories` | `CreateDirectoryRequest`, `Idempotency-Key` | 201 normalized `CatalogEntry` | Create empty/nested directories without files; existing ID with different intent conflicts |
| `POST /catalog/{id}/trash` | `RevisionPrecondition` | 200 updated `CatalogEntry` | CAS prevents duplicate/stale mutations |
| `POST /catalog/{id}/restore` | `RevisionPrecondition` | 200 updated `CatalogEntry` | CAS; target parent/name conflict is surfaced |
| `POST /files/{file_id}/head/{version_id}` | `RevisionPrecondition` | 200 updated `CatalogEntry` | Select a retained conflict version explicitly, with CAS |
| `GET /events` | Optional `Last-Event-ID` | 200 `text/event-stream` with bounded `Event` messages | Hints only; catalog revisions remain authoritative |

Binary chunk responses include exact `Content-Length`, `ServerSend-Chunk-SHA256`, `Content-Type: application/octet-stream` and `Cache-Control: no-store`; they do not include private names in disposition headers. V1 resumes at chunk boundaries, not byte ranges within an individual chunk. Chunk GET rejects `Range` with `invalid_request`/400; a dropped chunk is fetched again. Chunk PUT requires known content length (411 with `invalid_request` when absent), validates index/count/expected final position and negotiated body ceilings, and streams hashing/writes within bounded buffers. Request-body compression is unsupported; reject non-identity `Content-Encoding` with 415/`invalid_request`. Query values are not authorization or path material.

A future event/statistics implementation may add separate role-checked admin subscriptions. A user event stream never includes other accounts. Health/capabilities/proof remain the only public protocol routes; onboarding-only sessions cannot access any route above.

## Upload creation and durable acknowledgement

See [create-upload.json](../shared/api/testdata/create-upload.json) and [upload.json](../shared/api/testdata/upload.json). A client generates opaque logical file/version IDs before transfer and persists them with the job. A new logical file uses `expected_head:"0"`; an update uses the last observed per-file head revision. An absent `parent_id` means the account's virtual root. For an existing file the parent/mode must agree with the intended operation; moving between directories is an explicit catalog mutation, not an accidental upload side effect. A new version may choose a different storage mode without rewriting earlier versions. Private/standard siblings may coexist, but names within a private version always remain opaque.

Persist the exact manifest body before creation. `chunk_count`, `transmitted_bytes` and `manifest_bytes` describe its transmitted objects and encoded envelope, not the original private length. They are immutable for that upload generation. `CreateUploadRequest.Validate` checks feasible counts/lengths without overflowing; final validation checks actual descriptors. Empty files have count/length zero and a positive encoded manifest size. For the fixture, the standard manifest is exactly 384 bytes with no final newline; `manifest_bytes` is consequently 384. Adding whitespace changes that intent.

Reserve all relevant resource ceilings before accepting creation: user quota, committed objects, manifest, staged bytes and temporary destination-filesystem overlap. Distinct filesystems require separate reservations/free-space accounting. Storage workers enforce global/per-user concurrency and bounded buffers independently of the client. Return `capacity_exhausted` rather than accepting work that cannot be reserved. Creation does not publish a visible catalog head or consume unlimited per-file metadata in memory.

An idempotency key is a random opaque ID unique per account and operation. Store its normalized creation intent and outcome transactionally with the reservation. For finalization, bind the key to upload ID and SHA-256 of the exact manifest bytes; retries send the persisted identical body. The same key with different intent returns `conflict`; it never overwrites or reserves twice. Check authorization/revocation before returning any replayed result. Preserve creation/finalization results while the upload/version exists. After abandoned-upload cleanup, keep a bounded tombstone for at least the configured retry horizon (v1 minimum 30 days), returning `upload_gone` rather than recreating it. Clients never intentionally recycle keys or retry stale creation after that horizon; start a new generation after source reconciliation. Retention and tombstone cleanup are tested in the upload/cleanup chunks.

A chunk acknowledgement means both bytes and recoverable metadata are durable. Hash the transmitted bytes incrementally, compare the supplied digest/length, flush the immutable object and containing directory, then durably record its reference before acknowledging. Identical `(upload_id,index,length,digest)` retries are safe while open, finalizing or durably committed/conflicted, without rewriting accepted data; cancelled/expired uploads instead return `upload_gone`. any conflicting accepted index returns `conflict` and preserves the first object. Verify actual bytes, not just caller headers. Ownership, upload state, body length and missing/final index are checked by the service, not the metadata decoder. Partial bodies/checksum failures receive no durable success and are reconciled after reconnect.

Batched upload (advertised as capability feature `batch_upload`) publishes up to 256 empty or single-chunk standard files, at most `max_request_bytes` of data, in one request. Each entry carries the creation intent plus its exact manifest bytes (base64), validated exactly as creation and finalization would. The server stages and verifies every file, flushes all objects concurrently into one object shard, then commits every file as a committed upload, version and catalog entry in one transaction, with a savepoint per file. Refusals (invalid manifest, digest mismatch, missing parent, used IDs) are per file; capacity exhaustion refuses the whole batch. The desktop batches queued files of at most 1 MiB, up to 4 MiB per request, and uses individual uploads for larger files or servers without the feature.

Every non-final chunk of an upload has the same size, fixed by the first non-final chunk received, and the final chunk ends the file; chunks may arrive in any order. This places each chunk at one offset in the upload's file. Publishing a file whose name is taken by another visible file in that folder replaces it in the catalog and retains the replaced file's versions. A file and a folder cannot share a name; creating an existing folder returns that folder.

`MissingChunks` returns sorted, disjoint, coalesced half-open index ranges `[start,end)` within `chunk_count`. The page size counts **ranges**, not files or chunk indices. A new snapshot captures missing work at that point. The client checks upload ID and chunk count against its persisted intent before using a page. Concurrent acknowledgements may make a listed index unnecessary; resending identical data remains safe. Never expand a huge range into an in-memory whole-batch list. Reconcile all pages before deciding finalization is possible, then let finalization validate again. If a snapshot expires, start a new missing query; never infer success from a lost acknowledgement or an empty partial page.

## Upload and catalog transitions

| From | Allowed next states | Meaning |
| --- | --- | --- |
| `open` | `finalizing`, `cancelled`, `expired` | Accept new chunks only while open; one transactional winner claims finalize/cancel/expiry |
| `finalizing` | `committed`, `conflicted`, `open` | Recovery either publishes a durable outcome or rolls back to retryable open with no visible partial version |
| `committed`, `conflicted`, `cancelled`, `expired` | None | Immutable outcome; replay reads the recorded result without another transition |

Finalization claims the transition before cancellation/expiry can release resources. Cancel/expire only wins from `open`; a competing request during finalization returns `conflict`, and the caller queries/retries after recovery. Active finalization retains reservations and object references until it commits or rolls back. Terminal upload IDs are never reopened. A source mutation creates a fresh upload/version/idempotency generation; never combine chunks from two source fingerprints.

Finalization validates all of the following before publishing: authenticated scope matches manifest server/account; file/version/mode/count/length match immutable upload intent; actual manifest body length equals `manifest_bytes`; schema/private format is negotiated; chunk descriptors are contiguous, ordered, nonzero, within bounds and sum without overflow; every durable stored chunk has exactly the claimed length/checksum; capacity and parent/ownership are still valid. `ValidateFinalize` and `ValidateManifestBodyLength` cover structural binding; the storage service must enforce the durable-object and transactional checks.

When staging and data differ, copy into a temporary object **on the destination filesystem**, verify, flush, rename within that filesystem and sync its directory before committing a database reference. Never rely on cross-filesystem rename. Pending transitions/orphans are reconciled idempotently after crashes. A 200 finalize result implies all referenced objects and metadata survive restart; the server must not acknowledge earlier to improve apparent speed.

File head revisions and account catalog revisions are separate monotonic counters. Every catalog-visible mutation appends an account-scoped revision/change in the same transaction. Mutating an existing head requires exact `expected_head`; zero requires absence. `CheckRevision` implements equality, while the database performs the CAS atomically. On success, increment the per-file head revision and append a catalog change. A stale upload finalization still preserves its complete immutable version, leaves the newer head untouched, appends a catalog change to invalidate version listings, and returns 200 with `state:"conflicted"`, that version ID, current head revision and new catalog revision. This durable conflict outcome is distinct from a rejected mutation's typed HTTP 409. Replaying it cannot create another version. Users choose an explicit head later with a fresh precondition. Active uploads pin required parents/file records against destructive cleanup.

Trash is a catalog mutation with revision preconditions, not immediate object deletion. Restore and conflict selection also require fresh revisions and ownership. Purge/retention cannot remove objects referenced by active uploads, readers or retained versions. These persistence and cleanup properties are runtime acceptance work.

## Standard and private envelopes

[manifest-standard.json](../shared/api/testdata/manifest-standard.json), [manifest-empty.json](../shared/api/testdata/manifest-empty.json) and [manifest-private.json](../shared/api/testdata/manifest-private.json) define outer envelope examples. `schema_version:1` defines structural serialization, not the private cryptographic algorithm.

Every manifest binds server/account/file/version IDs, storage mode, total **transmitted** chunk bytes and an ordered `chunks` array. Each descriptor has zero-based `index`, `bytes` and lowercase SHA-256. Nonfinal chunks meet the minimum; the final chunk may be shorter but never empty. Empty standard files use `chunks:[]`, `total_bytes:0` and valid metadata. The server must independently know which index is final. Manifests are bounded before parsing; object bodies are streamed separately.

Standard mode requires `standard:{"name":"report.txt"}` and forbids `private`. The name is a single UTF-8 component of 1–255 bytes without traversal components, separators, NUL/control characters. Standard contents may be plaintext at rest. These logical-name rules do not replace download containment, symlink, reserved-name, Unicode/case collision or destination-platform validation.

Private mode requires only `private:{"format":"<negotiated ID>","payload":"<base64 ciphertext envelope>"}` and forbids `standard`. Payload bytes must be nonempty and the format must be explicitly supported by both peers. Production currently has **no approved private format**; passing an empty supported-format set rejects every private manifest. `test-only` merely exercises outer shape validation. Do not interpret it as encryption or upload support.

Chunk 17 must specify authenticated encrypted names/paths/original lengths and hashes, wrapped per-version keys, manifest authentication, key/nonce uniqueness and associated-data binding to server/account/file/version/index. It must bind the complete ordered descriptor list and metadata against substitution, truncation, duplication and reordering. Private empty-file representation, payload encoding, test vectors and retry-safe ciphertext staging are also gated there; the outer envelope alone does not authenticate them. Retransmissions use persisted identical ciphertext; a fresh encryption attempt uses fresh reviewed randomness and a new immutable generation. Never expose private names, original hashes, unwrapped keys or original sizes in public fields/logs. The server still sees ownership, transmitted sizes, counts and timing. Valid authenticated old catalogs may be replayed to a new device; v1 makes no complete malicious-server rollback guarantee.

## Catalog snapshots, history and events

Current runtime uses five-minute HMAC cursors bound to account, folder, limit, revision, snapshot and server instance. Revision changes, expiry and server restart require a fresh listing; pages are never silently combined across revisions. There is no retained delta history yet: `changes?after` returns an empty interval if unchanged, otherwise `snapshot_expired` and a full paginated refresh. The event stream below remains planned.


`CatalogPage` contains `snapshot`, `catalog_revision`, `entries` and optional continuation. The revision is the account's high-water mark at snapshot creation, unchanged across pages. Root is virtual; parent IDs are opaque and account-owned. Entries can be files or directories, standard/private, active/trashed. A file requires a head version ID; directories have no file version and can be empty. Entries carry positive per-entry `head_revision` and mode-appropriate metadata only. A private directory also has opaque encrypted metadata. In a default non-trash listing, tombstones never masquerade as live entries.

`VersionPage` is bound to one file, includes immutable manifest digests and exposes retained conflict versions for download/selection. Validate digests and account/file ownership on every manifest and chunk read, not just the first list request. Compare a fetched manifest's exact transmitted bytes with `manifest_sha256` before trusting it. The version's mode is immutable; later defaults or head changes cannot rewrite it.

For delta refresh, request `GET /catalog/changes?after=<last-completed-revision>`. `CatalogChanges` captures a stable interval `(from_revision,through_revision]`; every page keeps that interval and snapshot. Changes are ordered by strictly increasing decimal revision, each with opaque `id`, `removed` and an entry for upserts only. Trash/restores are upserts with changed `trashed`; permanent removal is an opaque tombstone. Assign a separate revision to each changed entry, even within a multi-entry transaction, then publish its final high-water mark. Changes after the snapshot wait for the next query. Persist the new high-water mark **only after all pages** have been applied atomically or checkpointed with their snapshot/cursor. Empty deltas use `changes:[]` and a valid interval. Expired history returns `snapshot_expired`, and the client replaces its catalog from a full paginated snapshot before continuing deltas. Comparing revisions lexicographically is incorrect; use lossless numeric comparison.

The event stream sends frames with `id: <sequence>`, `event: message` and one `data: <Event JSON>` line, followed by a blank line. Sequence is a positive, account-scoped decimal string and must match the JSON `sequence`. Bound each JSON message to 16 KiB, line/frame length and the consumer buffer; use comment heartbeats at most every 15 seconds to detect stale connections. Ignore unknown event types. `catalog_changed` requires `catalog_revision`; `session_revoked` closes the stream and refreshes authorization state; `statistics_changed` signals a bounded snapshot refetch. No event carries private names/keys or another account's details.

Send `Last-Event-ID` on reconnect. Invalid IDs fail with `invalid_request`; IDs older than retained history fail with `snapshot_expired` **before** opening the stream. Replay may duplicate messages; discard sequences already handled. On sequence gaps, expired history, disconnect or suspected staleness, reconcile catalog revisions/full snapshot and current authorization. A new stream without a replay cursor is followed by catalog reconciliation. Slow consumers are disconnected rather than blocking transfers; a bounded queue drop triggers the same reconciliation. Never treat event delivery as proof of storage durability or the revocation enforcement mechanism.

## Durable desktop queue

The current SQLite v2 runtime stores operational tasks as `queued`, `active`, wait/retry states, `paused`, `done`, `skipped`, `failed`, `cancel_pending`, `cancelling` or `cancelled`. Batch summaries are computed from these rows. Retry requeues only failed/cancelled tasks in that selection, preserving completed work and stable task IDs; it does not clone the selection. The shared `QueueState`/v1 foundation transition table below remains the logical job contract, distinct from those operational task states.

`QueueState` is local, not a synchronized server job. Scope every job/file task and acknowledgement by server/account, persist before networking, and checkpoint reasons/counters/cursors/source fingerprints. One unavailable profile must not block another. The scanner persists incremental work with bounded memory; file tasks can transfer while the batch scanner continues. Job-level `scanning` tracks discovery, and completing discovery checkpoints through `queued` before scheduling the final `running` stage. Do not require a whole-batch in-memory list or a scan-complete total before beginning useful work.

| From | Allowed next states |
| --- | --- |
| `queued` | `scanning`, `running`, `paused`, `cancelled` |
| `scanning`, `running` | `queued`, `paused`, `waiting_network`, `waiting_authentication`, `waiting_vault`, `waiting_capacity`, `retry_scheduled`, `complete`, `partial`, `cancelled`, `failed` |
| Paused or any waiting/retry state | `queued`, `paused` (when different), `cancelled`, `failed` |
| `complete`, `partial`, `cancelled`, `failed` | None; retry creates a new job referencing only unresolved items |

No self-transition is a mutation. On restart/resume/sleep-wake, checkpoint active work back through `queued` and reconcile persisted scanner tasks, source fingerprints and server acknowledgements before restarting workers. Waiting for authentication first attempts serialized silent refresh; waiting for a vault affects private work only. Network and capacity failures have distinct waiting states. Only transient, replay-safe operations enter bounded retry scheduling. A changed source starts a new upload generation; a missing source requires user action. Symlinks are skipped by default and unsupported/unreadable entries are reported. A live changing file cannot be promised a consistent snapshot.

Pause/cancel stops scheduling new file work, cancels active local streams and checkpoints completed acknowledgements before reporting success. Local cancellation can coexist with an already committed remote version; reconcile any finalization race and report it. It never rolls back completed server copies. `complete` means no failed/skipped items; `partial` means some completed and some skipped/failed; `failed` means no useful completion and unrecoverable failure. User cancellation is `cancelled` with truthful completed counters. Closing to tray retains workers; explicit quit checkpoints before exit. These actions require later native-platform and persistence tests.
