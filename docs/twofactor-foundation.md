# TOTP helper foundation

`apps/server/internal/auth/twofactor` uses the approved `github.com/pquerna/otp` library for enrollment and code verification. It is not an authentication service: HTTP endpoints, password checks, enrollment state, encrypted storage, rate limits and recovery codes remain separate work.

## Enrollment

`Enroll(accountLabel, qrSize)` creates a fresh 20-byte random secret, an `otpauth` provisioning URI and a QR PNG. It fixes the issuer to `ServerSend`, uses SHA1, six digits and a 30-second period. The caller supplies an account label that distinguishes its server/account. Labels must be valid UTF-8, 1–128 bytes, without colons, control characters or surrounding whitespace. The square QR size must be 256–1024 pixels.

The returned secret, URI and PNG all contain sensitive enrollment material. Show them only within the authorized provisional enrollment flow; never log them. Store the secret encrypted and activate enrollment only after successful verification. Generation errors return no partial enrollment and do not include input secrets.

## Verification and replay persistence

`Verify(secret, code, now, lastAcceptedStep)` takes an explicit clock and returns an accepted 30-second step. Codes must be exactly six ASCII digits; secrets must use the canonical 32-character Base32 form generated by enrollment. Importing legacy keys with different lengths or parameters is not supported. The accepted window is the current step plus or minus one, excluding negative counters. Pre-epoch times are invalid.

Initialize `lastAcceptedStep` to `NoAcceptedStep` (`-1`) for a new secret. Verification selects the newest matching step and requires it to exceed the saved watermark. A code accepted early through future skew consumes that future step as well: it cannot be accepted again when the server clock catches up. Failures return `NoAcceptedStep` and a typed sentinel error without the submitted code or secret.

The helper does not persist the watermark. Two concurrent requests with the same saved watermark can both pass this pure check. Before granting authentication, the caller must atomically compare-and-update the stored watermark from the value it read to the accepted step, coordinating with secret replacement and enrollment state. On a conflict, reload current state and reverify or reject. A successful enrollment verification also consumes its step. Invalid codes and replay errors should become the same external authentication failure; internal configuration/secret faults must not expose their sensitive input.

The verifier computes the TOTP counter explicitly and uses the library's HOTP verifier per counter so that it can report the exact accepted step; it does not implement its own cryptographic primitive. See the [library API](https://pkg.go.dev/github.com/pquerna/otp/totp) for standard enrollment parameters.

## Validation

Tests cover fresh-secret uniqueness, provisioning parameters and label encoding, QR dimensions/bounds, randomness failures, RFC 6238 SHA1 vectors reduced to six digits, step/skew boundaries, malformed input, epoch handling and replay rejection including future-window acceptance. Run the server check script and `go test -race ./internal/auth/twofactor` from `apps/server` with the approved dependencies available.
