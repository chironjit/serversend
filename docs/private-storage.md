# Private storage v1 (experimental)

The desktop asks once per server, before its library opens, whether to use standard storage or a **Private vault**; the choice is saved on the server profile (`vault_configured`) and can be changed under **Servers**. Choosing private creates a separate vault passphrase, requires acknowledging key loss, and requires exporting the recovery package to protected storage away from the server before continuing. Account password/TOTP recovery only restores account access. A clean device needs that access, the server's intact envelopes and ciphertext, and either the vault passphrase or exported recovery package. Use **Use recovery file** on the library's unlock prompt and paste the package, then restore files normally.

Standard work needs no vault. The mode selected for a new batch is captured in its durable tasks; the profile remembers the selection. Changing mode does not rewrite existing versions. Private directory names and file metadata decrypt locally. Concurrent updates to an existing private file use its opaque ID and expected revision, preserving conflicting versions. Concurrent devices creating the same previously unseen private name can create distinct IDs: resolve those visible duplicates by selecting a version/entry and trashing the unwanted entry. Uploads refuse ambiguous equal private names instead of guessing.

Unlock defaults to a fixed 15-minute timer, including active work. Configure 1–1440 minutes explicitly; private jobs wait on expiration and resume after unlock. Native credential storage is a separate opt-in from remembered account login; restoring a session alone never unlocks the vault. The explicit credential-store unlock button verifies its saved key against the remote vault. Lock clears decrypted catalog views; removing a profile also removes its remembered vault key. Turn off remembered vault storage to delete that local copy. Account sign-out clears the in-memory key, retaining an explicitly remembered native-store copy.

## Format and key rules

`serversend-private-v1` uses Go's [AES-256-GCM with generated 96-bit nonces](https://pkg.go.dev/crypto/cipher#NewGCMWithRandomNonce). Nonce and authentication tag add 28 bytes per object. Every fresh file attempt has fresh random 256-bit file key and version ID; the random 256-bit vault master wraps that key. Retransmissions read persisted ciphertext; they never regenerate nonces under an accepted version. Never exceed 2^32 encryptions per key. Emergency master-key rotation is outside this format's workflow.

The passphrase wrapper derives 32 bytes with [Argon2id](https://pkg.go.dev/golang.org/x/crypto/argon2#IDKey): version 0x13, independent random 16-byte salt, 64 MiB, three passes, one lane. Only these v1 parameters are accepted, before allocating KDF memory. One derivation runs at a time per process. A separate random 256-bit recovery secret wraps the same master without a password KDF. Recovery exports include format, server/account/vault IDs and this secret; never copy them into a server volume or backup. A master-encrypted confirmation string detects stale/incorrect remembered keys. Master, recovery and file keys originate from `crypto/rand`.

Envelope AAD is JSON `[format, scope, vaultID, purpose]`; purpose separates passphrase, recovery and confirmation. Creation requires revision 1. Atomic server compare-and-swap requires the next revision, unchanged identity, recovery wrapper and confirmation; password changes rewrap only the passphrase wrapper. Old devices must refresh after a race. Revision is a concurrency precondition, not an anti-rollback guarantee.

File AAD is JSON `[format, Binding]`. The frozen binding vector in `shared/vault/vault_test.go` pins spelling/order: server/account scope, FileID, VersionID, Kind, Index. Kinds separate `key`, `manifest`, `chunk` and `directory`; chunk index binds position. The encrypted manifest authenticates the exact ordered ciphertext chunk descriptors, original name, original length/hash and wrapped file key. Every object authenticates before plaintext publication; the full plaintext hash/length also verifies before publication. Unknown formats fail closed. The outer manifest contains only IDs, ciphertext sizes/digests and encrypted metadata. Private files/directories use opaque ID names on the host; topology, ownership, counts, sizes and timing remain visible.

Go JSON serialization is part of v1 AAD; another implementation must reproduce the frozen bytes. Cryptographic tests include an AES-GCM known-answer vector, binding vector, swaps, duplication, truncation, wrong scope/key, tampering, KDF bounds and fuzz seeds. This implementation review and passing tests do not replace an independent cryptographic review before production use.

## Persistence, bounds and recovery limits

The desktop persists private task paths, metadata and checkpoints encrypted under the scoped vault key in SQLite. It retains no plaintext private search/index cache. Private queue labels/errors are generic on disk. Decrypted catalog pages are bounded and discarded on lock. Plaintext restore files and their temporary publication files are local output and require normal endpoint disk protection. Go secret clearing is best effort, not protection against a compromised desktop or memory/swap inspection.

Private upload preparation uses at most one 4 MiB chunk buffer and a ciphertext-only staging file. Current private files must fit within 1 GiB including chunk overhead. Desktop private uploads run one at a time with an aggregate 8 GiB staging budget, counting paused attempts; resume or cancel them to reclaim space. Standard limits are unchanged. Ciphertext is flushed before saving a checkpoint and before server admission; saved acknowledgements reconcile missing server chunks on resume. A fresh expired/cancelled attempt receives new identities/randomness. Completed/cancelled private task stages are removed. Interrupted decryption reuses verified ciphertext download checkpoints and publishes only authenticated complete output; publication acknowledgement loss is reconciled using the encrypted original hash.

Server accounting reports standard logical content separately from private ciphertext bytes; physical allocation/reservations include encryption overhead. The server cannot report private plaintext sizes or decrypted names. Version history, trash, retention and stopped-server backups retain ciphertext and encrypted metadata using the same reference rules as standard versions.

A malicious/restored server can replay old valid envelopes, manifests or directory arrangements. There is no trusted cross-device monotonic freshness witness. Device revocation blocks future server requests; it cannot erase already copied keys/ciphertext/plaintext or undo offline passphrase guessing. Lost vault keys cannot be recovered by an administrator. Preserve external recovery packages separately from backups. The [backup procedure](backup-restore.md) now has a local private recovery drill; actual Unraid, Windows/macOS native credential stores/filesystems, large private-file staging and power-loss qualification remain open.

Local microbenchmarks (Linux amd64, Ryzen 9 8945HX, three iterations): Argon2id approximately 105 ms/unlock; 1 KiB object encryption approximately 4 µs, 2448 allocated bytes/op. Raw object overhead is 28 bytes (2.73% at 1 KiB); encrypted JSON manifests, key wrappers and SQLite add per-file overhead. These are format-cost samples, not deployment throughput claims. Re-run `go test ./shared/vault -bench .` on target hardware.
